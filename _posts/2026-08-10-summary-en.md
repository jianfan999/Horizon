## [Rust SIMD on the GPU: A Novel Approach](https://www.vectorware.com/blog/simd-on-gpu/) ⭐️ 8.0/10

The Vectorware blog post introduces a new technique for running Rust's portable SIMD code on GPUs, allowing developers to write SIMD-style operations for GPU compute. The approach has spurred active discussion about portability and implementation challenges. This work could let Rust developers reuse familiar SIMD abstractions for GPU programming, potentially improving developer productivity and performance in high-performance computing. It also highlights limitations in Rust's portable SIMD ecosystem, such as nightly-only availability and non-portable constant widths. The technique builds on Rust's unstable portable SIMD library, which is only available on nightly toolchains. Community members noted that the constant SIMD width requirement limits performance portability, and some have turned to crates like fearless_simd for stable alternatives.

hackernews · sagacity · Aug 10, 18:12 · [Discussion](https://news.ycombinator.com/item?id=49247477)

**Background**: SIMD (Single Instruction, Multiple Data) is a CPU technique that processes multiple data points with one instruction, whereas GPUs typically use SIMT (Single Instruction, Multiple Threads), where many threads execute concurrently. Rust's portable SIMD library provides explicit SIMD operations to write vectorized code without vendor-specific intrinsics. This blog post explores adapting that CPU-centric SIMD model to GPU execution.

## [SMM Bypass Exploits an Extremely Long Instruction to Break Firmware Quiescence](https://github.com/xoreaxeaxeax/smiiiiiiiiiiiiiiii) ⭐️ 8.0/10

A new exploit technique abuses System Management Mode (SMM) by using an extremely long instruction to prevent a CPU core from entering SMM when a System Management Interrupt (SMI) is triggered, allowing that core to attack another core that is already inside SMM. This technique exposes a fundamental assumption in SMM firmware that all cores are quiescent while one core handles the SMI, potentially letting privileged attackers bypass SMM protections and compromise firmware security. It may influence how platform vendors design SMI handlers on multi-core systems. The attack requires root privileges and relies on an instruction that takes longer than the SMM handler's timeout, causing a desynchronization between cores. The readme stresses the instruction must be 'very, very, verrrrry long' to outlast the firmware's IO-completion timeout.

hackernews · WhiteDawn · Aug 10, 16:03 · [Discussion](https://news.ycombinator.com/item?id=49245491)

**Background**: System Management Mode (SMM) is a privileged x86 operating mode triggered by a System Management Interrupt (SMI), used by firmware for low-level tasks like power management. SMM is non-reentrant and relies on the OS being suspended, so firmware assumes that no other code is executing while SMM runs. This exploit breaks that assumption by having one core still executing a long instruction when an SMI is broadcast, so the core does not enter SMM and can interfere with the SMM handler.

**Background**: Leveraged ETFs are exchange-traded funds that use financial derivatives and debt to deliver a multiple, usually 2x or 3x, of the daily return of an underlying index or asset. When many leveraged ETFs concentrate on the same AI stocks, forced buying or selling during rebalancing can amplify price moves. This is a known mechanism of volatility transmission, where shocks in one market segment spill over to other assets and markets.
