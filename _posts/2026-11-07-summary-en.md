## [China Reports First-in-Human Chemogenetic Trial, Cutting Epilepsy Seizures by 92.6%](https://www.scmp.com/news/china/science/article/3373500/kill-switch-epilepsy-china-cuts-seizures-926-first-human-chemogenetic-trial) ⭐️ 8.0/10

A Chinese research team has reported the first human trial of a chemogenetic 'kill switch' for epilepsy, using gene therapy to install engineered receptors in the brain that reduced seizures by 92.6% in patients with refractory epilepsy. It marks the first time DREADD (designer receptor exclusively activated by designer drug) technology has moved from animal models into human patients. Around one-third of epilepsy patients worldwide do not respond to any existing anti-seizure medication, and surgical resection of the seizure focus carries a risk of irreversible neurological damage. A reversible, remotely controllable approach could offer these drug-resistant patients an alternative to ablative surgery, and this result is an early translational milestone for chemogenetics as a clinical tool rather than a lab technique. Chemogenetics uses engineered receptors activated by a synthetic small-molecule drug rather than light, so neuromodulation is slower and longer-lasting than optogenetics but does not require implanted hardware. Because the therapy combines a gene-delivered receptor with a matching drug, regulators will likely treat it as a combined gene-plus-drug product requiring a dual approval pathway, and long-term safety of permanent receptor expression in the brain remains an open question.

rss · SCMP · Nov 6, 13:00

**Background**: Chemogenetics is a technique in which macromolecules are engineered to interact with small synthetic molecules that the body does not otherwise recognize, allowing researchers to switch specific populations of neurons on or off. It is conceptually similar to optogenetics, but substitutes a drug for light, trading millisecond precision for broader coverage and no need for fiber-optic implants. DREADDs are the best-known class of chemogenetic receptors; until now they had been used almost exclusively in animal research to probe the relationship between brain activity and behavior.

## [Libghostty 1.0 released: Ghostty's terminal core becomes an embeddable library](https://mitchellh.com/writing/libghostty-1-0) ⭐️ 7.0/10

Mitchell Hashimoto announced the 1.0 release of Libghostty, the embeddable library form of the Ghostty terminal emulator, making its terminal-emulation core available to other applications for the first time as a stable release. The milestone was met with downstream reports from developers already building on it, including an Android experiment, the Ghostel Emacs frontend, and at least one independent terminal project. Terminal emulation is notoriously hard to get right, so a small, reusable, MIT-licensed core means app developers no longer have to reimplement VT parsing and terminal state management themselves. This positions Ghostty less as a single terminal app and more as shared infrastructure for the broader ecosystem, spanning GUI toolkits, editors, web and mobile frontends. The core piece, libghostty-vt, is a portable, high-performance C library that is essentially zero-dependency (not even libc), handling VT sequence parsing, terminal state such as cursor position, styles, text reflow and scrollback, plus renderer state management; Libghostty overall exposes both a C and a Zig API. The existence of a deliberately minimal reference app, Ghostling, shows the library is meant to be embedded in very small hosts rather than only in full-featured terminals.

hackernews · mfiguiere · Nov 6, 23:30 · [Discussion](https://news.ycombinator.com/item?id=50399933)

**Background**: Ghostty is a fast, feature-rich, cross-platform terminal emulator that pairs platform-native UI with GPU acceleration, and it is written in Zig. Zig is a systems language designed to replace C while remaining ABI-compatible with it, which is why a library written in Zig can still be consumed from C, Swift, .NET or the web. Libghostty is the extraction of Ghostty's emulation engine into a standalone library, so that editors, terminals of other kinds, and applications can embed correct terminal behavior instead of writing their own.

## [Cheap 'Jev' judge that escalates to Opus matches Opus accuracy at 4x lower cost](https://hightouch.com/blog/llm-judges-identity-resolution) ⭐️ 7.0/10

Hightouch published a blog post showing that pairing a cheap decision model, Jev, with Claude Opus in an escalation setup matched Opus-level accuracy on an identity resolution task at roughly 4x lower cost. Instead of sending every case to the expensive model, Jev acts as a judge/router that decides which records need to be escalated to Opus and which it can resolve itself. The write-up gives a concrete, reproducible example of model orchestration economics: most traffic stays on a fast, cheap judge while only hard cases pay for the frontier model. For teams running high-volume classification or matching pipelines, this pattern is a practical lever on inference cost without an obvious accuracy penalty. Jev is not a text-generating LLM — it returns typed decisions (a choice, a score, or a yes/no probability) in roughly 70–500ms, which makes it a natural fit for the judge/router role. The result is scoped to a single identity resolution benchmark rather than a general claim about coding agents or broad LLM quality, and the escalation policy's design is what carries most of the cost saving.

hackernews · theanomaly · Nov 6, 19:48 · [Discussion](https://news.ycombinator.com/item?id=50397429)

**Background**: LLM-as-a-judge is a technique where one model assesses or labels the output of another against predefined criteria, widely used as a cheaper substitute for human annotation. Model routing is the related idea of keeping a pool of models and sending each request to the cheapest one likely to succeed, escalating to a stronger model only when needed. Jev, from TypeSafe AI, is described as a 'System One' model that outputs typed decisions instead of prose, replacing the prompt-and-parse loop used to extract a label from an LLM answer.

## [PwnEscape Part 2: Practical Firecracker microVM Escape Walkthrough](https://pwn.ai/blog/firecracker-escape) ⭐️ 7.0/10

The pwn.ai team published "Firecracker Escape: PwnEscape Part 2," a step-by-step guide showing how to weaponize the previously disclosed PwnEscape vulnerability (CVE-2026-99999) to break out of an AWS Firecracker microVM and reach the host. Unlike the original disclosure, which focused on the underlying Linux kernel networking flaw, this post documents the concrete exploitation chain against Firecracker's VMM. Firecracker underpins multi-tenant serverless and sandbox platforms such as AWS Lambda and Fargate, so a reproducible guest-to-host escape directly challenges the isolation assumption that makes dense microVM packing safe. The write-up gives defenders and cloud operators a concrete test case for validating patches and hardening layers rather than an abstract CVE description. The critical caveat is that the demonstrated configuration ran Firecracker with no jailer, meaning no privilege dropping, no namespace isolation, and no seccomp filtering were in place; a deployment using those controls would require a separate assessment of what an attacker can reach after compromising the VMM. The exploit builds on the original chain, which abused a Linux networking flaw to achieve repeatable host-memory disclosure and ultimately a full guest-to-host escape.

hackernews · SerCe · Nov 6, 19:33 · [Discussion](https://news.ycombinator.com/item?id=50397219)

**Background**: Firecracker is an open-source virtualization technology from AWS that creates lightweight "microVMs" using KVM; it deliberately strips out unnecessary devices and guest-facing functionality to shrink the attack surface and allow thousands of VMs per host. Because each microVM is meant to be a strong security boundary in multi-tenant environments, any escape from guest to host is treated as critical. Firecracker ships with a companion program called the jailer, which wraps the VMM process in cgroups, namespaces, seccomp filters, and dropped privileges so that a compromised VMM is still boxed in on the host.

## [Bare-metal UEFI programming tutorial sparks discussion of prior art and toolchains](https://kevinboone.me/efitest_index.html) ⭐️ 7.0/10

Kevin Boone published a step-by-step tutorial series at kevinboone.me that walks readers through writing bare-metal programs directly against UEFI firmware, without an underlying operating system. The guide covers the practical mechanics of building an EFI application, including the lack of a C standard library, linker behaviour with unresolved external symbols, and the Windows-influenced coding style inherent to EFI. UEFI is the first code that runs on virtually every modern PC, yet developing for it is poorly documented compared with user-space or kernel programming, so a clear hands-on walkthrough lowers the barrier for systems programmers, bootloader authors, and OS hobbyists. The accompanying Hacker News thread (192 points, 33 comments) turns the post into a hub of references, showing how much scattered knowledge exists around EFI development. The tutorial warns that the linker will not complain about calls to functions that do not exist; it simply marks them as external and the program crashes at runtime, and it suggests using `nm -D --undefined-only` in the build script to verify no undefined symbols remain. It also flags two recurring pain points: the absence of a C standard library and the 16-bit character (UCS-2/UTF-16) string handling that EFI mandates.

hackernews · LaSombra · Nov 6, 16:50 · [Discussion](https://news.ycombinator.com/item?id=50394855)

**Background**: UEFI (Unified Extensible Firmware Interface) is the specification for the firmware that runs first when a computer powers on, replacing the legacy BIOS; it is maintained by an industry consortium, with Intel's original EFI specification (last version 1.10, 2005) as its ancestor, and TianoCore EDK II as the reference implementation written in C. "Bare-metal" programming means writing software that runs with no operating system underneath, talking directly to the hardware and firmware services. Writing a UEFI application therefore means targeting the firmware's own boot services and protocols rather than POSIX or Win32 APIs, which is why tutorials must explain the missing libc and unusual string types.
